# Rings 기본계획

작성일: 2026-09-27  
상태: 리뉴얼 구현 중 · 2026-10-12 코드 대조
관련 문서: [세부계획.md](./세부계획.md) · [디자인.md](./디자인.md)

기본계획은 목적·메뉴·전체 흐름, 세부계획은 화면 구성·기능 동작, 디자인은 시각적 방향을 관리한다. 동일한 규칙은 담당 문서 한 곳에서 관리한다.

현재 구현: 데이터·앱 틀·편집기·날짜·글자·Print까지 연결되어 있다. 7단계의 Projects 정리·Diaries 관리·첫 다이어리 온보딩·Images/Fonts 관리·Colors 팔레트 보관과 불러오기, 다른 작업에서 페이지 가져오기·여러 페이지 관리 연결까지 구현했다. 로그인·클라우드는 다음 8단계, 편집 편의는 9단계다. 자세한 진행과 검증은 [진행상황.md](../../진행상황.md)에서 관리한다. 날짜가 붙은 과거 설명보다 뒤에 기록한 최신 결정이 우선한다.

## 1. 목적

Rings는 사용자가 자신의 다이어리 규격에 맞는 속지를 만들고, 여러 페이지를 구성하고, 실제 출력까지 준비하는 도구다.

이번 리디자인의 목적은 다음 두 가지다.

1. 복잡한 메뉴와 제작·인쇄 흐름을 단순하게 정리한다.
2. 세련되고 친근한 디자인으로 바꾸되, 편집기의 사용성을 우선한다.

가장 중요한 구조적 변화는 **양식 한 장 중심의 제작에서 여러 페이지로 된 작업 중심의 제작으로 확장**하는 것이다. 날짜가 채워진 결과 확인과 개별 페이지 수정도 제작 화면에서 완료할 수 있어야 한다.

## 2. 문서의 합의 수준

- **합의 방향**: 사용자가 직접 요청하거나 대화에서 명시적으로 확인한 내용.
- **설계 제안**: 합의 방향을 실현하기 위해 제시한 구체적인 방식. 검토 후 확정한다.
- **미정**: 동작 규칙이나 예외 처리를 추가로 결정해야 하는 내용.

이 문서는 개발 지시서나 구현 완료 보고서가 아니다. 화면 구성과 핵심 개념을 검토하기 위한 기준 문서다.

## 3. 현재 앱에서 확인한 출발점

지정된 Rings 소스에서 로컬 앱을 실행하고, 새 M5 양식을 통해 Template → Insert → Print 흐름을 확인했다.

- Template 화면은 여러 규격별로 새 양식을 만들 수 있는 구조다.
- Insert에는 페이지 편집과 AutoField 도구가 있다.
- Print에도 그리기·글자·자동필드 도구가 표시된다.
- 소스상 반복·날짜 세트 생성과 개별 출력 페이지 수정 기능이 존재한다.
- 이 때문에 양식 편집, 날짜가 채워진 결과 편집, 출력 준비의 경계가 사용자에게 불분명해질 수 있다.

확인 범위는 현재 제작·인쇄 구조와 관련 소스다. 전체 기능에 대한 회귀 검증이나 모든 자동필드 시나리오의 동작 검증은 수행하지 않았다.

## 4. 핵심 원칙 — 합의 방향

1. 메인 메뉴는 Create / Library / Learn 세 개로 구성한다.
2. Print는 독립 메인 메뉴보다 제작 흐름 후반의 액션으로 둔다.
3. 최초 질문으로 개인화하고, 사용자가 메인으로 쓰는 다이어리 크기를 그 사용자의 기본 규격으로 적용한다.
4. 하나의 작업에 표지·월간·위클리·데일리·메모 등 서로 다른 양식을 자유롭게 섞는다.
5. 중앙 편집 영역의 페이지를 세로로 스크롤하며 편집한다.
6. 기존 앱은 기능 파악을 위한 참고로 삼고, 좌측 세부 설정과 UI는 단순하고 일관되게 새로 설계할 수 있다.
7. 페이지 추가·삭제·복제·메뉴는 각 페이지 가까이에 둔다.
8. 별도 페이지 관리 영역을 상시 펼쳐 화면을 복잡하게 만들지 않는다.
9. 날짜·달력 결과와 개별 페이지 디자인 수정은 제작 화면에서 처리한다.
10. 만든 작업은 Library에 폴더로 정리하고, 다른 작업의 페이지를 가져와 다시 쓸 수 있게 한다.

## 5. 사용자는 무엇을 만들고 보관하는가

사용자는 **자신의 다이어리에 넣을 속지를 만들고, 여러 페이지를 하나의 작업으로 저장**한다. 따로 템플릿을 만들지 않고, 저장한 작업에서 페이지를 가져와 다시 쓴다.

예를 들어 주로 A5 다이어리를 쓰는 사용자라면 다음과 같다. A5는 설명용 예시이며 실제 크기는 사용자의 답변에 따라 달라진다.

1. 처음 질문에서 주로 A5를 사용한다고 답한다. 이 사용자의 기본 규격은 A5가 된다.
2. ‘10월 다이어리’라는 작업을 시작한다. 매번 크기를 선택하지 않아도 A5로 시작한다.
3. 그 안에 표지, 월간, 메모를 추가한다. 서로 다른 양식을 함께 구성할 수 있다.
4. 저장한 ‘10월 다이어리’ 전체를 Library에서 다시 열어 편집한다. 이것이 **내 작업**이다.
5. 다음 달 작업에서 ‘10월 다이어리’의 메모 페이지를 **가져와** 다시 넣는다. 자주 쓰는 양식만 모아둔 작업을 폴더에 따로 두어도 된다.
6. 사용할 이미지와 글꼴 파일도 Library에서 관리한다.
7. 완성하면 Print에서 출력할 종이와 배치를 정한다. 속지 크기와 프린터에 넣는 종이 크기는 다를 수 있다.

즉, **작업은 만들고 있는 결과물 전체**, **페이지는 그 안의 속지 한 면**이다. 개념은 이 둘뿐이다. 작업은 한 페이지로만 구성해도 된다. 페이지를 가져와도 원래 작업은 바뀌지 않는다(복사).

미정: 한 작업 안에 서로 다른 규격까지 섞을지 여부. 합의한 혼합 범위는 서로 다른 양식이다. 사용 규격을 여러 개 등록하는 것과 한 작업에 여러 크기를 섞는 것은 별개다.

## 6. 메인 메뉴와 기능 배치

| 메뉴 | 주된 목적 | 포함할 내용 |
|---|---|---|
| Create | 새 작업 시작 | 기본 규격의 빈 페이지로 시작, 편집기로 진입 |
| Library | 내 작업과 자료 관리 | 내 작업(폴더로 정리), 이미지 파일, 글꼴 파일 관리, 다시 편집·Print |
| Learn | 만들고 활용하는 방법 이해 | 시작 안내, 규격·종이·바인더 참고 자료, 제작·인쇄 가이드 |

설계 제안:

- Library는 내 작업 / 이미지 / 글꼴을 관리한다. 내부 탐색 UI의 형태는 세부계획에서 검토한다.
- 기존 Template 기능(양식 목록)은 Library의 작업 목록과, 편집기 안의 ‘다른 작업에서 페이지 가져오기’로 나뉜다.
- 기존 Insert 편집 기능은 Create에서 진입하는 통합 제작 화면의 중심이 된다.
- 기존 Print의 개별 내용 편집은 제작 화면으로 이동하고, 출력 설정은 Print에 남긴다.
- Notebooks와 Examples의 기존 기능 범위·콘텐츠는 추가 확인 후 재배치한다. 실제 기능 삭제는 아직 확정하지 않는다.

### 결정 (2026-09-27)

- **Create는 빈 페이지로 시작한다.** 앱이 제공하는 기본 템플릿은 첫 버전에 없다. 기본 템플릿은 코드가 아니라 콘텐츠 제작이므로 나중에 추가한다.
- **낱장 조합(칸 배정)은 없앤다.** 서로 다른 양식을 한 종이에 찍으려면 한 작업 안에 그 페이지들을 넣는다. 따로 저장한 작업 두 개를 한 종이에 합쳐 찍는 기능은 두지 않는다.
- **Learn은 블로그 형태로 운영한다.** 앱 사용법, 인쇄 팁, 다이어리 종이 정리, 타공기 등 제품 소개와 링크를 글로 올린다.
- **Print는 두 곳에서 들어간다.** 편집 화면 상단 버튼과, 저장한 작업 목록의 작업 카드.
- Notebooks는 리뉴얼 전까지 숨기고, 나중에 Create 하위 탭으로 되살린다.

- **메뉴 이름 ‘My Rings’는 ‘Library’로 바꾼다.**
- **‘내 템플릿’을 두지 않는다.** Library의 작업은 한 목록이고 폴더로 정리한다. 폴더는 첫 버전에 넣는다. 한 장짜리와 여러 장짜리를 구분하지 않는다. 다시 쓰고 싶은 페이지는 편집기에서 ‘다른 작업에서 페이지 가져오기’로 넣는다. Canva·미리캔버스도 같은 구조다([레퍼런스분석](./레퍼런스분석.md)).

## 7. 최초 진입과 개인화

### 합의 방향

- 처음에 몇 가지 질문으로 사용 환경을 파악하고 개인화한다.
- **사용자가 메인으로 사용하는 다이어리 크기가 그 사용자의 기본 규격**이다. 앱 전체에 고정된 M5 기본값을 두는 것이 아니다.
- 이후 새 작업은 해당 사용자의 기본 규격으로 시작하므로 매번 크기를 고를 필요가 없다.
- 나중에 사용 규격을 추가하거나 변경할 수 있다.

### 설계 제안

1. 사용하는 다이어리 크기를 선택한다. 복수 선택을 허용한다.
2. 메인으로 사용하는 다이어리를 확인하고 그 크기를 기본 규격으로 정한다. 하나만 사용하면 해당 크기를 적용한다.
3. Create에서는 기본 규격을 미리 적용한 빈 페이지로 시작한다.
4. 사용 규격 관리와 현재 작업 크기 변경을 분리한다. 사용 규격 추가가 기존 작업을 변경하지 않는다.
5. 규격을 모르는 사용자를 위한 안내 또는 선택 유예 경로를 제공한다.

개인화 질문의 개수·문구와 규격 외 질문은 아직 미정이다.

결정 (2026-09-27): 온보딩은 **처음 Create를 누를 때** 보여준다. 둘러보러 온 사람을 막지 않고, 크기가 실제로 필요한 순간에 묻는다.

### 결정 (2026-10-01) — 규격 대신 ‘내 다이어리’

- 사용자는 **내 다이어리**를 등록한다. 다이어리 = **이름 + 크기 + 실측값(세로·타공 위치 등)**. 같은 M6라도 브랜드·바인더마다 실측이 다르면 따로 등록한다.
- 온보딩에서 **첫 다이어리를 등록**한다. 프리셋(A5·M6 등)을 고르면 기본값이 채워지고, 실측이 다르면 고친다. 그 다이어리가 **기본 다이어리**가 된다(앞의 ‘기본 규격’).
- 이후 화면에는 **등록한 다이어리만** 보인다. 프리셋 목록은 다이어리를 새로 등록할 때만 나온다.
- 다이어리 관리(추가·실측 수정·기본 바꾸기)는 **Library → Diaries** 탭에서 한다.
- 결정 (2026-10-12): 온보딩의 **‘잘 모르겠어요’**는 속지 가로·세로를 자로 재고 구멍 수를 세는 짧은 안내를 보여주고, 재기 어려우면 **M6로 시작**한다(나중에 Diaries에서 바꿀 수 있다고 알린다). 온보딩 질문은 첫 버전에서 다이어리 하나만 묻는다.
- 다이어리는 **종이 치수**를, 폴더는 **정리**를 맡는다. 서로 대신하지 않는다.
- 3단접이는 다이어리가 아니라 **페이지 종류**다(예: M6 다이어리에 3단접이 페이지 추가).

## 8. 기본 제작 흐름

```text
첫 사용: 개인화 질문 → 주 사용 다이어리 크기를 기본 규격으로 설정
                              ↓
홈 → Create → 빈 페이지 → 여러 페이지 편집 → Print → PDF
홈 → Library → 저장 작업 열기 ─────┘      ↑
              └─ 작업 카드에서 바로 ──────┘
홈 → Learn → 제작·규격·인쇄 안내
```

제작 화면에서는 페이지를 추가하거나, 다른 작업에서 페이지를 가져오거나, 여러 장 복제하거나, 날짜를 채운 페이지를 생성한다.

Print에서는 출력 용지, 양면 출력, 용지 위 배치, 재단선 등 출력 조건을 다룬다. 내용 수정이 필요하면 해당 페이지의 제작 화면으로 연결한다.

화면 구성과 페이지 가져오기·반복 페이지 상세는 [세부계획](./세부계획.md), 시각적 방향은 [디자인](./디자인.md)에서 관리한다.

## 8-1. 기존 양식을 새 구조로 옮기기 (2026-10-06 결정)

새 버전은 **새 이름의 브라우저 저장소**를 쓰고, 처음 열 때 옛 저장소(`diary-designer`)를 읽어 **복사만** 한다. 옛 저장소는 건드리지 않아 옛 버전도 계속 돌아간다. 문제가 생기면 새 저장소만 지우고 다시 복사한다.

| 지금 있는 것 | 새 버전에서 |
|---|---|
| 일반 양식 | 작업 1개, 페이지 1장(뒷면이 있으면 앞뒤) |
| 반복 양식(N장) | 작업 1개, 같은 페이지 N장 |
| 날짜 세트 양식 | 작업 1개, 원본 + 날짜 페이지들(기간 그대로). Print에서 고친 페이지는 그 페이지의 개별 수정으로 |
| 노트 | 옮기지 않음(옛 저장소에 남음) |
| 이미지·글꼴 | Library → Images·Fonts |
| 양식 색(메인·서브) | 작업 색상(기본·POINT) |
| 양식들의 크기 | 같은 크기끼리 묶어 ‘내 다이어리’로 자동 등록 |
| 칸 배정 설정 | 버림 |

## 8-2. 로그인·클라우드 (2026-10-06 추가)

공동작업자의 `origin/feat/auth` 브랜치에 로그인·계정 관리·클라우드 저장(PocketBase)이 있다. 리뉴얼에도 들어가야 한다.

- 지금 그 클라우드는 **한 사람에 작업 한 벌**을 통째로 덮어쓴다. 글꼴·이미지 파일은 올라가지 않는다.
- 리뉴얼은 작업 여러 개·폴더·휴지통·다이어리·팔레트가 있으므로 **서버 구조를 작업마다 한 칸씩** 다시 짠다. 배포 전이라 처음부터 새 구조로 짠다.
- 2026-10-06 확인: `feat/auth`와 `feat/rings-print-2`는 합쳐도 **글자 충돌이 없다**(시뮬레이션). 저장 형식 판이 1→2로 올라 있으므로 합친 뒤에는 두 사람 모두 합친 코드를 써야 한다.
